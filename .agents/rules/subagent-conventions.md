# Subagent 协作规约

本规约适用于 `.claude/agents/` 与 `.codex/agents/` 中的 8 个专门角色。工具配置按各客户端原生格式维护，业务职责、验收标准与交接要求保持一致。

## 主 agent 负责协调

- 主 agent 收集需求确认、OpenSpec 规划审批与批次检查结果，再委派有明确范围的任务。
- Claude Code 可根据描述自动委派；Codex 在用户明确要求或适用项目规则 / Skill 要求时委派。角色文件的存在本身不要求启动全部角色。
- 这 8 个角色默认只完成收到的任务，不自行继续拆分并启动子 agent。确需进一步拆分时，向主 agent 返回建议与依赖；由主 agent 决定并安排。
- 主 agent 负责安排 `spec-reviewer` 的 Spec 合规审查与 `code-reviewer` 的代码质量审查；角色完成局部任务，不代表整个 change 已通过验收。

## 任务路由与并行策略

| 任务 | 承接者 | 边界 |
|---|---|---|
| 现状探索、调用链与受影响文件定位 | 主 agent 使用客户端内置探索角色 | 返回证据与文件位置，不修改实现 |
| 需求范围、用户故事、业务验收 | `product-manager` | 不编写技术 design 和工程 tasks |
| 页面流程、组件状态、视觉反馈规格 | `interaction-agent` | 不实现业务代码 |
| 技术 design、API 契约与工程 tasks | 主 agent 汇总前后端角色的分析 | 确认规划后才分配实施任务 |
| 功能实现与对应 RED → GREEN 测试 | `frontend-agent` / `backend-agent` | 实现者拥有所分配功能的测试文件 |
| 独立契约、集成、E2E、边界遗漏与回归 | `test-agent` | 不与实现者并行编辑同一测试文件 |
| 需求覆盖 / 代码风险 / 体验证据审查 | 对应的三个审查角色 | 仅返回发现，不修复实现 |

- 优先并行探索、文档查证、日志分析和审查；子 agent 只带回与当前决策有关的摘要。
- 前后端并行写入前先确定 API 契约、任务依赖与文件所有权；相同文件的写操作串行安排。
- 测试缺口分析可以与实现并行，最终回归和验收在待验代码稳定后运行。
- 简短、无需隔离上下文的任务由主 agent 直接完成；不为了用满角色或并发名额而派发。

## 委派时交齐输入

不要假定子 agent 已获得完整对话、用户审批或最新工作区状态。每个任务至少包含：

```text
角色与任务：<agent-name / task-id>
目标：<本次需要完成的行为或分析>
输入：<change 路径、相关 specs/design/tasks、必要的用户决策>
审批状态：<已确认的规划与允许执行的阶段；未知则标明>
可修改范围：<文件或目录；只读任务写“无”>
依赖：<先决任务、已确定的 API 契约、需要等待的结果>
验收：<可检查的条件与验证命令>
返回：<改动或发现、证据、偏差、未完成项>
```

## 子 agent 执行边界

- 开工先确认根目录 `AGENTS.md`、本规约及角色所列分域规约；已由客户端加载且可确认的内容直接沿用，其余按任务补读，避免重复输出整份规约。确认输入与当前文件一致。
- 修改业务代码前，必须有已确认的 OpenSpec 规划与实施授权；不清楚审批状态时先返回主 agent 核实。产品 / 交互角色仅修改任务授权的文档，测试角色仅修改任务授权的测试与测试配置。
- 多个 agent 共用工作区时，不回退他人修改；遇到文件重叠或冲突，先交由主 agent 协调。主 agent 只并行派发文件范围互不冲突、依赖已满足的任务。
- 发现范围扩大、设计冲突或缺少工具 / 环境时，报告具体阻塞和需要的输入，不擅自改变方案或放宽权限。
- 子 agent 不自行提交、推送、更新 submodule 指针或归档；这些动作由主 agent 根据用户授权统一安排。

## 审查职责与权限

- `spec-reviewer`、`code-reviewer`、`experience-agent` 仅报告发现，不修改任何文件，不运行会产生文件或改变服务状态的命令。
- 角色指令属于行为约束。Claude 的 `tools` 是工具白名单；Codex 子 agent 继承父会话权限，自定义 TOML 不能通过 `sandbox_mode` / `approval_policy` 创建独立沙箱。
- Codex 的严格只读审查应放在以 `codex --sandbox read-only` 启动的父会话中。不要把 TOML 中的注释或正文描述当作权限隔离。
- 体验审查需要页面、截图或浏览器操作结果时，只使用实际提供的证据或已授权的工具；证据不足就标注“未验证”，交由主 agent 补齐，不能仅凭源码宣布视觉或交互达标。

## 交接报告

默认使用下面的精简格式。完整对账矩阵、长日志和报告模板仅在任务明确需要时返回；审查角色不为保存报告而写文件，需持久化时交给主 agent。

```text
状态：完成 / 部分完成 / 阻塞；task-id：<如有>
结果：按重要性排序的改动或发现，附文件位置和依据。
验证：实际命令、退出状态、结果摘要与证据来源。
剩余：未验证项、设计偏差、未完成项和需主 agent 决定的问题。
```

- 实现任务保留 RED → GREEN 的证据；按严重性报告所有已确认问题，不为追求短摘要而隐藏高风险发现。
- 验证区分“自己运行”“主 agent 提供的结果”和“尚未验证”，不把历史任务勾选或示例输出当作本次验证。
- 没有发现问题仅代表本次范围与证据内未发现问题；缺少证据时不能给出“全部通过”或“可以上线”的结论。
